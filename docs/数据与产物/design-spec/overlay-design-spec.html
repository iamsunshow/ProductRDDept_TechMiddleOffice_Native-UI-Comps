Overlay 遮罩层 · 设计规格（基础组件 #6，subcategory=basics · 门禁 A）

组件 ID：ui.overlay　｜　定位：全屏遮罩 + 自定义内容插槽，作为弹窗/抽屉/引导/气泡菜单等浮层的通用底部基座。业务浮层一律基于 Overlay 组合（二次开发），禁止自行手写遮罩。
组件库版本 设计阶段锁定基线 = v1.3.12（C1 实现升级为 v1.4.0 MINOR：基础类 6/6 收官）

01 · 组件用途 & 不适用边界（SCQA）

维度说明
适用场景① 模态弹窗遮罩（二级操作确认）；② 浮层引导遮罩（新手引导、新手蒙版）；③ 加载/阻塞操作全屏遮罩（业务层 loading 全屏）；④ 抽屉/底部弹层/气泡菜单等的遮罩背景；⑤ 点击空白关闭的任何临时浮层
不适用（N/A）① 页面级固定半透明 Banner（非遮罩，归页面）；② Toast/Notify 通知浮层（不归 Overlay 管理，为独立组件 ui.toast / ui.notify）；③ Loading 局部小遮罩（归 EmptyState 或 loadingContent 插槽，非全屏级）；④ 页面路由级过渡（归 Router）
五态适配Overlay 为"容器型组件"，五态=视觉遮罩 + 插槽内容自身状态。因此：禁用/加载/成功/失败 N/A（由插槽内容自带），默认态 ✅ = 遮罩显示+内容插槽默认。另提供 关闭态（visible=false）由动画驱动。
与现有组件关系deps=[] 无依赖（不引入第三方动画库）。会被未来 Dialog / Popup / ActionSheet / Drawer / Popover 等浮层类继承组合。与 ConfigProvider 正交：遮罩颜色/圆角/间距读 DesignToken（零硬编码）。

要素Token数值说明

03 · 关键决策 PREP / ACE（人为决策 4 条，编号 P1–P4，待用户门禁 A 表决）

P1 · 遮罩层级 z-index / window 挂载方案：ACE 三选

选项后果评估
A：iOS = addSubview 到最外层 keyWindow；Android = Compose Dialog 原生弹窗容器✅ 真正全屏、跨页面、层级最高；Android 依赖 Dialog 自带 window 管理；iOS 须手动管理 UIWindow。双端内部实现不同但 API 一致。推荐 A：与现有弹窗行为一致。后续多 Overlay 叠加由调用时序控制栈序（业务保证）。
B：作为普通容器挂在父视图树中（需要业务给根容器锚点）① 层级低于导航栏/Tabbar 会被遮挡；② 父子布局冲突溢出；③ 每个业务接入都要暴露根容器接口 → 接入成本高淘汰：业务接入摩擦大、层级被遮挡常见 bug 源
C：iOS UIPresentationController / Android BottomSheetDialog 专用绑定单一场景（抽屉/底部弹），通用性弱，无法覆盖 Modal 对话框 / 全屏引导 / 加载遮罩淘汰：限定场景不可复用

P2 · 动画能力：只做淡入淡出（MVP）还是 位置/缩放/自定义 transition

选项后果评估
A：一期仅淡入淡出（fade 200ms，关闭可关闭），不开放自定义曲线✅ 双端 1:1 代码量最小；视觉一致性有保证。抽屉/底部弹/缩放需求由上层组件（Dialog/Popup）在插槽内容层自行实现（Overlay 仅做遮罩 base）推荐 A（一期 MVP）：职责边界清晰。过渡动画扩展留作 v1.4.x PATCH，不阻塞 6/6 基础类收工。
B：开放 enterAnimation/exitAnimation 插槽（双端不同，API 分裂）iOS CAAnimation / Android Transition 类型不同，跨端 API 无法 100% 对齐 → 违反治理规范双端一致铁律淘汰

P3 · 点击遮罩背景（非内容区）行为 & 穿透 clickThrough

选项后果评估
A：默认 closeOnMaskClick=true（点击遮罩背景关闭触发 onClose）；另提供 clickThrough=false（默认）拦截点击、true 穿透到底下页面✅ 默认行为与 NutUI Modal 一致；closeOnMaskClick 与 clickThrough 正交：clickThrough=true 时遮罩层不接任何事件（完全透明穿透用于气泡菜单/局部浮层），closeOnMaskClick 失效符合直觉。事件回调 onMaskClick?: () => void推荐 A：覆盖 90% 用例；onMaskClick 便于埋点。
B：closeOnMaskClick 默认为 false 强制业务关与主流组件库默认相反，业务易漏回调导致"关不掉"用户投诉 bug淘汰

P4 · 内容插槽布局位置（contentPosition）：居中 / 顶部 / 底部 / 左上 / 左下 / 右上 / 右下

选项后果评估
A：枚举 9 点 'center' | 'top' | 'bottom' | 'left' | 'right' | 'top-left' | 'top-right' | 'bottom-left' | 'bottom-right'，默认 'center'；另补 contentOffset?: {x,y} 微调✅ 完全覆盖 Modal/顶部通知/底部抽屉/角标气泡；双端布局对齐（Swift UIStackView/Jetpack Alignment 都可实现 9 点）；x/y 用统一逻辑 pt/dp推荐 A：覆盖 Dialog(center)/Drawer(bottom)/Toast-like(top)/Tooltip(corner) 四大场景
B：只默认 center，其余由业务写绝对定位写死场景窄，业务每次要重复写 safe-area 偏移淘汰

05 · 双端差异（登记 docs/平台差异.md）

项iOS（UIKit）Android（Compose）对齐结果
全屏挂载方式UIApplication.shared.keyWindow?.addSubview；z-order 由 addSubview 时序决定Compose Dialog(properties = DialogProperties(usePlatformDefaultWidth=false, decorFitsSystemWindows=false)) 内嵌，自动独立 windowAPI 不一致但对外 visible 参数一致。双端差异白名单登记。
系统返回键物理不存在，通过 onClose 关闭Android 返回键默认关闭 Dialog（Compose Dialog 原生行为）→ 通过 dismissOnBackPress 布尔属性暴露，默认 true补独立属性 dismissOnBackPress?: boolean（仅 Android 生效，iOS 读值忽略不报错）。登记平台差异。
圆角实现layer.cornerRadius + maskedCorners（顶部圆角生效于 bottom 抽屉）RoundedCornerShape(topStart/topEnd/bottomStart/bottomEnd) 按 contentPosition 自动计算掩膜圆角视觉一致，为内部实现差异，业务无感知。

06 · API 预览（门禁 B 定稿完整契约，见 review-overlay-B.md + api.json）

面速览
Props（10）visible: boolean 必选 / maskColor?: 'default' | 'transparent' | rgba-string 默认 default / closeOnMaskClick?: boolean 默认 true / clickThrough?: boolean 默认 false / contentPosition?: 9 点枚举 默认 center / contentOffset?: {x:number, y:number} / contentRadius?: 'sm'|'md'|'lg'|number 默认 0 / animation?: boolean 默认 true / dismissOnBackPress?: boolean 默认 true（仅 Android 生效）/ content: slot 必选（自定义内容插槽）
Events（2）onClose?: () => void（遮罩点击关闭 / 系统返回键关闭统一走这里）；onMaskClick?: () => void（仅遮罩被点击时触发，与 onClose 正交）
deps / 五态deps=[]（零依赖）；默认态 ✅，加载/成功/失败/禁用 N/A（插槽内容自带）
