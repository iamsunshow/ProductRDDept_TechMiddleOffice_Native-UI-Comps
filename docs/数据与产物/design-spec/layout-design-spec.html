Layout 布局 · 设计规格（布局组件 #3，subcategory=layout · 门禁 A）

组件 ID：ui.layout ｜ 定位：横向弹性分栏容器（Row/Col 栅格），对标 NutUI Layout（Row/Col）/ Ant Design Row/Col 的轻量版。用于统计双栏卡片、详情 label-value 行、筛选/工具组行、图标+文字水平组等「一行内按比例/自适应排布多个子内容」的场景。
组件库版本 设计阶段锁定基线 = v1.4.0（2026-09-04，未过 C2/D 不升版）

01 · 组件用途 & 不适用边界（SCQA）

维度说明
适用场景① 概览/统计页双栏卡片（如 本月收入/支出 1:1，span 6+6）；② 详情页 label-value 行（label 窄列 + value 宽列，span 3+9 或 4+8）；③ 筛选条件/工具按钮行（三~四个等宽或不等宽操作并排）；④ 图标/头像 + 文字水平组合（auto 内容并排 + 统一间距）
不适用（N/A）① 等分宫格图标入口矩阵 → Grid（ui.grid）；② 仅需子项统一间距、无比例诉求 → Space（ui.space）；③ 整行可点击列表项（含图标/箭头/副标题） → Cell（ui.cell）；④ 页面级骨架模板（导航栏+滚动内容+底部操作区，纵向三段） → 业务页面模板层（Layout 一期不做纵向页面骨架）；⑤ 吸顶/吸附 → Sticky（ui.sticky）
五态适配Layout 为「纯布局编排」组件，本身无交互与状态。默认态 ✅ = 子内容按 span/gutter/alignment 正常排布。点击/禁用/加载/成功/失败 N/A（子内容自身的交互与状态由各自内容组件承担，Layout 不内建任何状态）
与现有组件关系deps=[DesignTokens]（AppSpace 等）零硬编码。与 Grid（宫格=等分 items 自动折行）互补：Grid 面向「N 个同类入口等分」，Layout 面向「任意类型子内容按比例排布」；与 Space 划界：Space=纯间距工具（subview 数组 + 统一 gap），Layout=比例分栏容器（span 体系）；Layout 内可自由嵌套 Grid/Cell/卡片等任何内容组件

02 · 尺寸/颜色/圆角 Token 规格（零硬编码，引用 design-token.json）

要素Token数值说明
容器背景/边框/圆角—透明Layout 为 pass-through 容器：背景/边框/圆角由放入的子内容组件（Card 等）自己负责，Layout 不绘制任何装饰，避免叠层污染
子项水平间距（gutter）AppSpace.xs~xl4/8/12/16/24row 内相邻 Col 间距；默认 AppSpace.md=12（P3 待表决）
子项垂直对齐规则顶部对齐（行高 = 子项内容自然最大高度）一期两端一致：内容顶部对齐、行高取最高子项（等高拉伸 / center / end 对齐二期引入，双端契约同步；2026-09-04 门禁 B 前修订）
分栏比例（span）规则1~12（12 栅格）span/12 占父容器宽；双端实现：iOS Col 宽=父宽×span/12（constraint multiplier），Android Modifier.weight(span/12f)
字号/颜色——Layout 无自有文本，文字样式由子内容决定（子内容引用 AppFont/AppColor）

03 · 关键决策 PREP / ACE（人为决策 4 条，编号 P1–P4，待用户门禁 A 表决）

P1 · 组件形态：ACE 三选

选项后果评估
A：Row/Col 双组件（Row=行容器；Col=子项，自带 span 1~12）✅ 声明式嵌套（Row 内 2~4 个 Col），贴近 NutUI Row/Col 行业惯例；Android 命名 LayoutRow/LayoutCol 防与 Compose 内置 Row 冲突；iOS LayoutRow/LayoutCol（去 View 后缀规范）。双端 API 一致性好，span 语义直白。推荐 A：标准、可读、可扩展；Col span 体系双端 1:1 对齐成本最低
B：单组件 LayoutRow + addCol(span:content:) 方法式填充少一个类，但业务写法冗长（逐段 add），嵌套层级表达能力弱于声明式。淘汰：声明式弱，写复杂分栏不直观
C：页面骨架 Layout（Header/Content/Footer 三段模板）面向「整页纵向骨架」的另一种组件方向，与 Row/Col 分栏职责不同。可选二期方向（若业务页面骨架诉求出现再立 Page/Skeleton 组件）；一期 Layout 定位=分栏容器，避免与 SafeArea/页面层混职

P2 · 栅格基数（span 取值范围）：ACE 三选

选项后果评估
A：12 栅格（span 1~12）✅ 常用比例（1:1=6+6、1:2=4+8、1:3=3+9、1:1:1=4+4+4）全可表达；实现简单（span/12）。推荐 A：记账/通用场景最常用比例覆盖足够，双端实现最简
B：24 栅格（span 1~24）粒度更细（可表达 5:19 等），但业务几乎用不到，实现与心智成本更高。淘汰：一期过度设计
C：无固定基数，纯 flex 权重（子项任意 int 权重）灵活但缺统一约束：不同页面写 1:1 可能用 2:2/5:5…比例不一致，跨端换算易错。淘汰：无栅格约束会引入比例漂移

P3 · gutter 默认值：ACE 三选

选项后果评估
A：默认 AppSpace.md=12，可覆盖✅ 双栏卡片/工具行间距 12 视觉舒适且为组件库常见节奏（Grid 标题间距同为 md）；业务可传 xs/sm/lg/xl 或 0 覆盖。推荐 A：默认即合理，少配置
B：默认 0（业务必须显式传 gutter）显式但繁琐：绝大多数场景都要间距，漏传则内容贴死。淘汰：反直觉，默认应贴合多数场景
C：固定 md 不可配置API 最简但失去弹性（紧凑工具行想用 8 无解）。淘汰：不提供覆盖太死

P4 · 子项换行支持：ACE 三选

选项后果评估
A：一期单行不换行（超宽由内容自行适配/截断）✅ 满足统计双栏/label-value/工具行全部一期场景；实现最简；chips 流式多行场景确实存在但可用二期 wrap 支持。推荐 A：一期克制，覆盖已立项场景
B：一期即支持 wrap（子项超出自动折行）流式 chips 可用，但双端折行语义对齐成本高（iOS 需额外容器），且 Col span 与折行语义易混。淘汰：一期放大复杂度
C：二期再加 wrap（P4=B 一期不实现，登记需求）需求登记不实现=在规划内。记入 P4 附注：wrap 列为二期候选（需求待出现）

05 · 平台差异预告

维度iOSAndroid差异说明
行容器实现LayoutRow = 纯约束链（子项宽 = 父宽 × span/12 multiplier；顶部对齐；行高=内容 max）LayoutRow = Compose Row 封装 + 子项 Modifier.weight(span/12f)，verticalAlignment = Top系统原生架构差异，span 数学语义一致（span/12），两端行为对齐
子项 span 实现LayoutCol 宽 = 父宽 × span/12（NSLayoutConstraint multiplier）Modifier.weight(span / 12f)数学语义一致（span/12 占宽），数值两端同为 span 输入
gutterUIStackView.spacing（pt）Row horizontalArrangement spacing（dp）同取 AppSpace token 值（xs/xs=4 等）
子项内容定高内容须四边钉满 LayoutCol（内容高驱动行高）Box 内内容自然高，Row 高 = 最高子项两端一致：行高 = 子项内容自然最大高度；卡片等高 = 内容同构（D1/D4 Demo 自洽）；等高拉伸对齐二期（双端契约同步引入）
命名LayoutRow / LayoutCol（无 View 后缀）LayoutRow / LayoutCol（避开 androidx Row/Column）双端同名同 API
