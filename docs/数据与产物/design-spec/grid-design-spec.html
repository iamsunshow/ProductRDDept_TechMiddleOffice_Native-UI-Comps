Grid 宫格 · 设计规格（布局组件 #2，subcategory=navigation · 门禁 A）

组件 ID：ui.grid ｜ 定位：多格图标入口矩阵，对标 Ant Design Grid / 九宫格。用于首页快捷入口、发现页导航、功能菜单等场景。
组件库版本 设计阶段锁定基线 = v1.4.0

01 · 组件用途 & 不适用边界（SCQA）

维度说明
适用场景① 首页快捷入口矩阵（4~5 列 × 1~3 行）；② 发现页/我的页功能导航分区；③ 更多功能页全量入口网格；④ 任何「图标 + 文字」等分矩阵布局
不适用（N/A）① 单块可点击内容容器 → 用 Card（ui.card）；② 纯文字列表入口 → 用 Cell（ui.cell）；③ 横向滑动标签 → 用 Tabs（ui.tabs）；④ 复杂卡片内嵌多组件 → 用自定义布局
五态适配Grid 为"静态展示 + 点击交互"组件。默认态 ✅ = 网格正常展示。点击态 ✅ = 每项可点击 + 回调。禁用/加载/成功/失败 N/A（网格入口无状态切换需求；若业务需要禁用某项，由 data 层过滤实现，组件不内建）
与现有组件关系deps=[] 无硬依赖。内部引用 DesignTokens（AppColor/AppRadius/AppSpace/AppFont/AppIcon）零硬编码。与 NavBar 关系：iOS 现有两层封装 NavigationGrid→NavBar，Android 单层 Composable 直接实现（评审决策 P1 讨论是否统一）。

03 · 关键决策 PREP / ACE（人为决策 4 条，编号 P1–P4，待用户门禁 A 表决）

P1 · 组件命名：ACE 三选

选项后果评估
A：保持 NavigationGrid（与 api.json id=ui.grid 不一致但代码不改）代码类名 NavigationGrid，api.json id=ui.grid。开发者需记忆映射关系。淘汰：命名不一致增加认知负担
B：重命名为 Grid（与 api.json 一致，iOS 去 View 后缀规范）✅ 代码类名 = api.json id 去掉前缀。iOS: Grid.swift，Android: Grid.kt。双端 1:1 对齐。推荐 B：命名一致性优先。NavigationGrid 是历史遗留名（记账批次快速实现），正式评审后应统一到 Grid。
C：重命名为 GridView（保留 View 后缀）违反 iOS 组件无 View 后缀规范（已决策记录）。淘汰：违反已有命名规范

P2 · 双端图标尺寸差异（24pt vs 26dp）：ACE 三选

选项后果评估
A：统一为 26（iOS 24→26pt）✅ 双端视觉完全一致。26pt 在 iOS 上略大但差异可忽略。推荐 A：双端一致性优先，2pt 差异在视觉上几乎不可辨
B：统一为 24（Android 26→24dp）双端一致但 Android 图标略缩小。可选，但 26 是设计稿原始值
C：保持差异（iOS 24 / Android 26）双端视觉微差，用户可能注意到。淘汰：无必要差异

P3 · 列数（column）支持：ACE 三选

选项后果评估
A：column 作为 prop 暴露（api.json 已定义 column:number），默认 4✅ 灵活支持 3/4/5 列。Android 用 weight(1f) 天然等分只需改列数；iOS 用 .fillEqually 同理。推荐 A：api.json 已定义此 prop，实现成本低
B：固定 4 列，不暴露 column prop简化 API 但失去灵活性。淘汰：与 api.json 契约冲突
C：支持 column + 自动换行（超过 column 数量自动折行）类似 CSS flex-wrap，items 超过一行自动排多行。可选扩展（P3=C 时一期不实现，二期考虑）

P4 · 分区标题（title）是否为必选：ACE 三选

选项后果评估
A：title 可选（空字符串时不显示标题区域）✅ 更灵活：有标题=带分区网格，无标题=纯网格卡片。适配更多场景。推荐 A：空 title 时隐藏标题 + 节省垂直空间
B：title 必选（始终显示标题行）简单但不够灵活。淘汰：限制使用场景
C：title 可选 + 支持自定义标题视图过度设计，一期不需要。淘汰：MVP 不需要

06 · API 速览（门禁 B 冻结前草案）

类别名称类型必填说明
Propscolumnnumber否列数，默认 4
data{icon, text, id}[]是入口数据数组
titlestring否分区标题（空=不显示，P4 决策 A）
