SafeArea 安全区 · 设计规格（布局组件 #5 · 任务清单 #10，subcategory=layout · 门禁 A）

组件 ID：ui.safe-area ｜ 定位：安全区避让容器——把内容限制在系统安全区（刘海/状态栏/圆角/Home Indicator/手势区）之内，对标 Flutter SafeArea / Android WindowInsets / iOS safeAreaLayoutGuide 的跨端统一封装，让双端页面内容自动避开系统遮挡。
组件库版本 设计阶段锁定基线 = v1.4.0（2026-09-04，未过 C2/D 不升版）

01 · 组件用途 & 不适用边界（SCQA）

维度说明
适用场景① 页面级内容避让：顶部内容不压状态栏/刘海，底部操作栏不贴 Home Indicator/系统手势区；② 自定义 header/沉浸式页面的安全区留白；③ 横屏圆角遮挡避让；④ 深浅色状态栏随页面内容自绘时，安全区内边距与内容色板分离
不适用（N/A）① 系统栏颜色/图标明暗 → SystemBars（foundation.system-bars）（iOS StatusBarNavigationController / Android ConfigureSystemBars）；② 键盘弹出避让（imePadding）→ 二期候选；③ 安全区内的布局排版 → 页面自身布局职责（Space/Layout 编排）；④ 手势下拉/转场动画适配 → 非组件职责
五态适配纯适配容器，无自身交互与状态。默认态 ✅ = 子内容自动位于安全区内。点击/禁用/加载/成功/失败 N/A
与现有组件关系deps=[DesignTokens]（零视觉 token，仅间距语义）。与 SystemBars 划界：SystemBars=「栏自身」外观（颜色/明暗/透明），SafeArea=「内容避开系统区域」的内边距适配；两者可叠用（页面配置栏色 + 内容套 SafeArea）。双端一致性基础：iOS safeAreaInsets（UIViewController 提供）vs Android WindowInsets.safeDrawing 语义对齐（P3 表决）

02 · 尺寸/Token 规格（零硬编码）

要素Token说明
避让数值系统 insets（运行时）不自定义数值：top=状态栏/刘海高、bottom=Home Indicator/手势区高、left/right=圆角/刘海侧距，全部取系统实时值（iOS safeAreaInsets / Android safeDrawing），机型自适应零硬编码
容器视觉—透明 pass-through：零绘制零背景，装饰由子内容承担
子内容对齐规则默认贴安全区四边排布（内容从安全区原点起排），与页面布局组件（Layout/Space/Grid）正常嵌套

03 · 关键决策 PREP / ACE（人为决策 4 条，编号 P1–P4，AI 代评待用户总审）

P1 · 组件形态：ACE 三选

选项后果评估
A：容器式 SafeArea { content }（内容自动避让）✅ 声明式最简：双端同构 Box 包装（iOS 约束到 safeAreaLayoutGuide / Android windowInsetsPadding）；业务零手写 insets 判断。推荐 A：覆盖 90% 场景、心智负担最低、双端 1:1 易验证
B：仅取 insets 值的函数（返回 EdgeInsets 由业务自己 pad）灵活但每个调用点都要手动拼 Modifier/padding，业务易漏/混用，失去组件统一语义。淘汰：退回手工适配=没有组件
C：容器 + insets 取值函数双 API功能全但一期 API 面积翻倍，insets 取值实际业务多可交由容器内部完成。淘汰：容器一期足够，取值函数遇真实诉求再补

P2 · 避让边（edges）模型：ACE 三选

选项后果评估
A：可配四边 top/bottom/left/right（默认全边）✅ 对齐 Flutter SafeArea 语义；沉浸式顶栏/底栏等需要"只避单边"的真实页面可显式裁剪。推荐 A：默认全边零参数，特殊页显式裁剪
B：仅 top+bottom 二档（仿 antd-mobile SafeArea position）行业有先例但忽略刘海横屏 left/right 圆角场景，且竖屏全边默认即 top+bottom，裁剪需求少。淘汰：antd 是 Web 壳场景，原生需四边覆盖
C：不分边，强制四边API 最简但沉浸式页面（如 tab 底部自绘背景）无法只避底/只避顶。淘汰：缺少裁剪入口会导致业务绕过组件手写

P3 · Android insets 数据源：ACE 三选

选项后果评估
A：WindowInsets.safeDrawing（statusBars+navigationBars+displayCutout 聚合）✅ 一次覆盖状态栏/刘海/手势条/圆角，随系统变化自动更新，Compose 官方推荐聚合源。推荐 A：语义即"安全区"，与 iOS safeAreaInsets 对齐
B：手动 statusBars+navigationBars 组合漏 displayCutout（刘海/挖孔）在部分机型会压字。淘汰：组合易漏项
C：安全区全由系统 Activity 主题处理与沉浸式自绘需求冲突，无法页面级控制。淘汰：组件语义需要代码级可控

P4 · 一期范围裁剪：ACE 三选

选项后果评估
A：一期仅容器式安全区避让（top/bottom 为主，四边可配）✅ 覆盖页面级/沉浸式/底栏全部一期场景；键盘避让与横屏动画等登记二期候选。推荐 A：一期克制、双端同构、可即时验收
B：一期追加键盘 imePadding 避让Android imePadding 现成但 iOS 需键盘通知联动，双端不对称且键盘场景与"安全区"语义分属两件事。淘汰：键盘避让另行立项（ui.keyboard 类）
C：一期提供 SafeAreaInsetsProvider 全局注入（可测试性）为单测抽象但组件库一期无单测基线，抽象成本>收益。淘汰：登记二期（C1 单测补建时再引入注入点）

05 · 平台差异预告

维度iOSAndroid差异说明
数据源UIViewController.safeAreaInsets（safeAreaLayoutGuide）WindowInsets.safeDrawing（聚合）系统原生差异；均由系统实时计算，数值不可硬编码
容器实现SafeAreaView：普通 UIView，内部按 superview 的 safeAreaLayoutGuide 约束子内容四边（edges 可裁剪）SafeArea(edges){ content } = Box(Modifier.windowInsetsPadding(WindowInsets.safeDrawing.only(edges)))仅框架层差异，对外语义一致（edges 位掩码对齐）
edges 表示OptionSet<Edge>（top/bottom/left/right）Set<SafeAreaEdges>（枚举值）枚举语义一一对应
命名SafeAreaView（iOS 已有 UIKit 类冲突规避？无同名——组件用 SafeArea 别名类名若冲突则 SafeAreaView）SafeArea（Compose 无内置同名）P1 表决后统一双端命名

06 · API 速览（门禁 B 冻结前草案）

类别名称类型必填说明
Propsedgestop/bottom/left/right 集合否避让边，默认四边全避
Children—任意内容（1 个容器子内容）—容器子内容套安全区内边距排布

使用示例（草案）：SafeAreaView(edges: [.top, .bottom]) { 页面内容 } / SafeArea(edges = setOf(SafeAreaEdges.Top, SafeAreaEdges.Bottom)) { 页面内容 }
