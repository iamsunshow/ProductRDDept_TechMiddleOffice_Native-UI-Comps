# TMO 组件库 · 组件验收标准（acceptance）

> 地位：**组件从设计到落地的唯一验收标准与门禁清单**。与 `治理规范.md`（治理/发版流程）、`开发规则.md`（规则/打包/业务库约束）配套使用。
>
> 核心原则：**设计先行 → API 先 check → 实现 → 验收**。每道门禁通过才进入下一阶段，把返工拦截在成本最低的阶段。

---

## 一、总体流程（五阶段 + 门禁拆分）

```
阶段 1  设计        （无代码）设计规格沉淀 + ②设计测试用例（deps 前置须已完成）
              ┌── 门禁 A：设计评审通过 ──┐  不通过 → 返工设计，不动代码
阶段 2  API 契约    （无代码）api.json 契约 + ④API 测试用例
              ┌── 门禁 B：API 评审通过 ──┐  不通过 → 只改契约，不动代码
阶段 3  实现        （双端代码）双端并行实现，按用例 ID 逐个实现测试函数
              ┌── 门禁 C1：自测对齐 ──┐  单测 + 快照比对 + 用例映射核对，不通过 → 修复
阶段 4  CR + 合并   PR 评审 + CI 门禁
              ┌── 门禁 C2：CR + CI ──┐  不通过 → 打回修复
阶段 5  发版 + 业务落地   发版（Demo/CHANGELOG/tag）→ 业务 App 真实接入组件 → 度量降本
              ┌── 门禁 D：业务落地验证 ──┐  接入失败 → 回退排障 / 组件回修
```

> 与 `治理规范.md` 第五节「文档/Figma 先行 → Token 更新 → 双端并行开发 → Demo 更新 → 自测对齐 → 统一发版」衔接：本文件的门禁 A/B 把"先行"具体化、可评审、可验收。

### 1.1 验收顺序：列表顺序 + 依赖优先

- **顺序来源**：`docs/组件进度.md` 任务清单（第 3 节，按分类从上到下），一个组件一个组件走完门禁 A → B → C1/C2 → 发版 → 业务落地。
- **依赖优先（叠加约束）**：该组件的 `deps`（依赖组件）必须先于它完成。如 Cell 依赖 Icon/Image，则先完成 Icon/Image 再动 Cell，避免"组件完成了、依赖还没实现"。
- 每个组件走完后更新进度文档（达成情况 + 状态），再取列表下一个组件。
- 已实现（✅）组件不重复走流程；【暂未使用】组件跳过（见 1.2）。

### 1.2 【暂未使用】跳过机制

- 业务用不到的组件：在 `组件进度.md` 标注 **⏭ 【暂未使用】**，跳过全部门禁，不占用验收资源。
- 跳过原因在备注列登记（如「业务无此场景」）。
- 后续业务需要时，改回 ⬜ 重新入队即可。
- **季度复查**：每季度扫一遍 ⏭ 清单，业务有变化（新场景出现）则重新入队。

## 二、设计先行（如何落地 + 如何验收）

### 2.1 设计规格怎么落地

每组件一份设计规格，沉淀到 `www/`（组件文档站「设计参考」页，H5 形式，读写 Figma/Sketch 成本高时以此为准）或 `docs/design-spec/`。内容模板（**七项必填**）：

| 项 | 说明 |
|----|------|
| 组件用途 | 一句话功能 + 适用场景（与 `组件分类.md` 分类表一致） |
| 五态定义 | 默认 / 禁用 / 加载 / 成功 / 失败（不适用的标注 N/A） |
| 尺寸规格 | 宽高 / 间距 / 圆角 / 字号 / 色板，**全部引用 `design-token.json`，禁止硬编码** |
| 交互细节 | 点击反馈、动画、手势、弹窗层级 |
| 双端差异 | 系统级差异（手势 / hover / 键盘 / 控件样式），需登记 `平台差异.md` |
| 与现有组件关系 | 复用 / 组合 / 依赖的组件 id 列表（写 `deps`） |
| 设计参考图 | H5 规格页（`docs/design-spec/`，如 cell-design-spec.html） |

### 2.2 设计如何验收（门禁 A：设计评审清单）

- [ ] 规格模板七项齐全
- [ ] 所有颜色/尺寸/圆角/字号均引用 token（零硬编码）
- [ ] 五态齐全或逐项标注 N/A
- [ ] 交互细节完整（含点击反馈、加载态行为）
- [ ] 双端差异已说明并登记 `平台差异.md`
- [ ] 与现有组件无重复（已在分类表核对，无重复轮子）
- [ ] 设计参考图可查看（H5/SVG/截图）

> **评审通过 → 冻结设计 → 进入 API 阶段。** 设计不通过只返工设计，绝不带病进入代码，从源头避免大面积返工。

## 三、API 先 check 再实现

### 3.1 组件提供哪些 API、包含哪些能力

每个组件在 `api.json` 中定义完整契约（字段见 `开发规则.md`）：

| 能力面 | 字段 | 说明 |
|--------|------|------|
| 属性 Props | `props`（`开发规则.md` 第七节二期字段） | 属性名 / 类型 / 默认值，双端 100% 对齐 |
| 事件 Events | `events` | 回调名 / 签名，双端一致 |
| 方法 Methods | `methods` | 命令式接口（如有） |
| 能力标签 | `capabilities` | 检索标签（能力别名） |
| 场景 | `scenarios` | 典型使用场景（检索语料） |
| Token 依赖 | `visual_tokens` | 依赖的 token 名列表 |
| 组件关系 | `deps` | 依赖的其他组件 id |
| 平台状态 | `platforms` | 双端 available / partial / unavailable |
| 对外摘要 | `apis` | 对外接口摘要（契约文档 `开发规则.md` 的数据源） |

### 3.2 API 如何验收（门禁 B：API 评审清单）

- [ ] `id` 符合命名规范（`ui.*` / `foundation.*`，与分类表一致）
- [ ] props 双端命名/类型/默认值 100% 对齐
- [ ] events 回调签名双端一致
- [ ] 五态能力覆盖（或标注不支持）
- [ ] `capabilities` / `scenarios` 已填（保证可被检索命中）
- [ ] `visual_tokens` 已声明，且 token 已存在于 `design-token.json`（新增 token 先入库再评审）
- [ ] `platforms` 状态与实际计划一致
- [ ] 通过 `api.json` schema 校验（`开发规则.md` 字段合法）

> **评审通过 → 冻结契约 → 双端按契约并行实现。** API 不通过只改契约，不动代码。契约冻结后实现阶段禁止单端私自改 props/事件名（违反 `治理规范.md` 红线）。

## 四、功能验收（门禁 C 之一：测试门禁）

### 4.1 测试分层（按成本从低到高逐步覆盖）

| 层 | 对象 | 方式 |
|----|------|------|
| 逻辑层 | foundation（MoneyFormat / Calendar / Router / Storage…） | 纯单元测试（XCTest / JUnit），**先做** |
| 组件层 | 组件五态渲染（默认/禁用/加载/成功/失败） | 状态渲染测试 |
| 交互层 | 点击 / 事件回调 | 交互测试 |

### 4.2 门禁规则

- 双端单测接入 CI，**未通过 → 禁止 merge、禁止打 tag 发版**（与 `ui-version.json` 发版联动）
- 组件实现 PR 必须附带测试用例，缺失 → Review 打回
- 新增组件默认要求：逻辑层全覆盖 + 组件层五态覆盖
- **用例即代码（C1 自动核对）**：验收文档中的用例 ID（② D1-D8、④ A1-A7）与测试函数一一对应（命名如 `test_D1_defaultState`）。CI 脚本核对用例表 ↔ 测试代码：某个用例 ID 无对应测试函数 → 门禁 C1 不通过。

## 五、样式验收（门禁 C 之二）

### 5.1 token 硬编码校验（CI 自动）

- 扫描 `ios/*.swift` + `android/*.kt`，颜色/尺寸/圆角/字号必须引用 `design-token.json` 生成的资源
- 违规 → CI 报错（拦截硬编码，保证"样式符合设计规范"可机器校验）

### 5.2 设计一致性（人工走查 + 快照比对，均为门禁 C1 项）

- **人工走查**：实现 PR 提交时，Reviewer 对照「设计参考页」逐项走查（尺寸/间距/圆角/字号/五态视觉）
- **快照比对（门禁 C1 显式项）**：Android Roborazzi / iOS Swift SnapshotTesting，双端截图与设计参考比对，差异超阈值 → C1 不通过

## 六、落地验收 · 场景 A（双端实现 + 严格 CR 机制）

### 6.1 "组件已实现"的完整定义（六条件缺一不可）

1. `api.json` 有该组件记录（契约冻结）
2. 双端代码真实存在（iOS + Android）
3. 测试用例存在且通过（门禁 C1/C2）
4. Demo 可运行（`demo/ios` + `demo/android`）
5. 文档站可见（`www/` 组件页 + 设计参考）
6. **业务接入实例**（门禁 D）：业务 App 已真实接入该组件，替换一处自绘实现（见第七章）

### 6.2 CR 机制（强制）

**PR 强制清单**（缺一打回）：
- [ ] API 契约更新（`api.json` + `开发规则.md`）
- [ ] 测试用例
- [ ] Demo 更新
- [ ] CHANGELOG 记录
- [ ] 双端版本同步（`治理规范.md 第六节`：一端变更两端同版本）

**Review 检查清单**：
- [ ] 双端命名 / API 100% 对齐（`组件审计.md` 生成依据）
- [ ] 全部引用 token，零硬编码
- [ ] 测试通过（CI 门禁）
- [ ] 无重复造轮子（与分类表核对）
- [ ] 子模块变更单独提交（`治理规范.md` 3.3 铁律）

**分支保护**：`main` 禁止直推，PR + CI 门禁通过才可 merge。

## 七、落地验收 · 场景 B（业务真实使用 + 降本度量）

> TMO 的价值 = 降低业务研发成本。若业务代码库的量/复杂度没有可度量的下降，组件库即无效投入。

### 7.0 业务落地验证（阶段 5 · 门禁 D）

每个新组件发版后，走一次**真实接入**，才算验收闭环：

1. 在业务 App 选一个用到该组件场景的页面，把自绘实现**替换为 TMO 组件**（最小改动接入）
2. 记录替换前后：该页面 UI 代码量（行数 / 方法数）、自研率变化
3. 产出接入记录：`docs/验收流程/usage-<组件名>.md`（替换位置 / 前后代码量 / 遇到的问题）
4. **门禁 D 结论**：✅ 接入成功且代码量下降 → 验收完成；❌ 接入失败 → 回退排障（组件问题 → 回门禁 C1 修复）

> 无法立即接入的组件（业务暂无页面）→ 标注 ⏭【暂未使用】走季度复查，接入实例补记录后验收。

### 7.1 核心指标

- **业务自研率** = 业务库自研 UI 代码量 ÷ 业务总 UI 代码量（**目标持续下降**）
- 统计工具：`scripts/measure_adoption.py`（扫描业务库，识别未引用 TMO 的自绘 UI 代码）
- 进阶（中期）：复用向量检索做**轮子检测**——业务代码片段与组件描述做相似度匹配，自动发现"疑似重复造轮子"

### 7.2 降本度量报告

- 定期（每迭代/季度）输出：自研率、业务 UI 代码量趋势、业务复杂度指标（页面控制器平均代码量等）
- 用数据回答：TMO 到底帮业务减了多少代码

## 八、门禁汇总

| 门禁 | 触发点 | 检查内容 | 不通过后果 |
|------|--------|----------|-----------|
| A 设计评审 | 设计规格完成 | 模板七项 + token 引用 + 五态 + 差异 + 无重复 | 返工设计，不动代码 |
| B API 评审 | 契约定义完成 | 命名对齐 + 能力覆盖 + schema 合法 + token 存在 | 只改契约，不动代码 |
| C1 自测对齐 | 实现完成 | 双端单测 + 快照比对 + 用例映射核对（用例即代码） | 修复后再验 |
| C2 CR + CI | PR 提交 / merge | PR 清单 + Review 清单 + CI（单测 + token 硬编码校验） | 打回，禁止 merge |
| D 业务落地 | 发版后接入 | 业务真实接入 + 代码量下降（`docs/验收流程/usage-<组件名>.md`） | 回退排障 / 组件回修 |

## 九、评审操作流程（设计 & API 如何验收）

### 9.1 角色分工

| 角色 | 职责 |
|------|------|
| 产出方（组件负责人 / AI） | 产出设计规格与 API 契约，生成可查看的 H5 页面，发起评审 |
| 评审人（业务/技术负责人，即你） | 打开页面逐项打勾、给结论（通过 / 打回）、填备注 |

评审形式：**异步评审**（打开页面 + 勾选 `docs/验收流程/评审清单.md` 清单 + 备注），不需要开会；关键组件可同步过一遍。

### 9.2 设计验收流程（门禁 A）

| 步骤 | 产出方动作 | 评审人动作 |
|------|-----------|-----------|
| 1. 产出 | 写设计规格（七项模板）→ 运行 `scripts/generate_design_gallery.py` 生成**自包含 HTML 设计规格页**（视觉渲染 + 尺寸标注 + 五态 + token 引用） | — |
| 2. 交付 | 给出 HTML 页路径/链接（浏览器打开即看，无需代码） | 打开页面 |
| 3. 评审 | — | 对照「设计评审清单」逐项打勾（见 `docs/验收流程/评审清单.md` 第一节） |
| 4. 反馈 | 根据备注修改设计规格（**不写代码**） | 在清单填备注 / 结论 |
| 5. 结论 | 冻结设计 → 进入 API 阶段 | ✅ 通过 / ❌ 打回 |

### 9.3 API 验收流程（门禁 B）

| 步骤 | 产出方动作 | 评审人动作 |
|------|-----------|-----------|
| 1. 产出 | 基于通过的设计，在 `api.json` 定义契约 → 生成 **API 契约页**（www 组件详情页，展示 props / events / methods 表格） | — |
| 2. 交付 | 给出契约页链接 + 关键 API 表 | 打开页面 |
| 3. 评审 | — | 对照「API 评审清单」逐项打勾（`docs/验收流程/评审清单.md` 第二节） |
| 4. 反馈 | 根据备注修改契约（**不写代码**） | 填备注 / 结论 |
| 5. 结论 | 冻结契约 → 双端开始实现 | ✅ 通过 / ❌ 打回 |

### 9.4 贯穿规则

- **验收产物一律 H5 页面**（HTML 设计规格页 / www 文档站），你打开浏览器即可验收，不接触代码、不需要装工具。
- 每轮评审产出**评审意见单**（`docs/验收流程/评审清单.md` 复制填写），留档可追溯，打回有据。
- 两道门禁都在代码之前：打回成本 = 只改文档，**从源头避免返工**。

### 9.5 组件验收文档标准（每组件必交付 · 四要素）

每个组件的验收文档 = 一份《组件验收文档》（按 `docs/验收流程/验收模板.md` 模板），**四要素缺一 → 评审打回**：

| 要素 | 内容 | 产出阶段 | 验收门禁 |
|------|------|----------|----------|
| ① 设计细节 | 设计规格 H5：用途 / 五态 / 尺寸（引 token）/ 交互 / 双端差异 / 组件关系 / 参考图 | 阶段 1 | 门禁 A |
| ② 设计测试用例 | 用例清单：五态渲染、尺寸与 token 取值、交互反馈（ID 映射测试函数） | 阶段 1 | A + C1 |
| ③ API 设计细节 | `api.json` 契约：props / events / methods / capabilities / scenarios / visual_tokens | 阶段 2 | 门禁 B |
| ④ API 测试用例 | 用例清单：属性取值、事件回调、能力覆盖（ID 映射测试函数） | 阶段 2 | B + C1 |

- 测试用例在阶段 1 / 2 **定义**（随验收文档评审），阶段 3 **实现并执行**（用例 ID ↔ 测试函数一一对应），执行结果随 PR 提交（门禁 C1 自动核对）。
- 验收文档命名：`docs/验收流程/component-acceptance-<组件名>.md`（由模板复制）。

## 十、术语

| 术语 | 含义 |
|------|------|
| 设计先行 | 阶段 1 设计评审（门禁 A）通过后才进入 API/代码阶段 |
| API 先 check | 阶段 2 契约评审（门禁 B）通过后才开始双端实现 |
| 依赖优先 | 组件 `deps` 必须先于该组件完成（在列表顺序之上叠加的约束） |
| 用例即代码 | 验收文档用例 ID（D*/A*）与测试函数一一对应，CI 自动核对 |
| 五态 | 默认 / 禁用 / 加载 / 成功 / 失败（组件状态统一基准） |
| 业务自研率 | 业务库未引用 TMO 的 UI 代码量占比（目标持续下降） |
