> **唯一权威治理文档**：仓库架构、收纳约定、版本铁律、发版流程、业务接入、迭代机制。

## 一、目标与解决的历史痛点

TMO 组件库的治理目标：

| 痛点        | 现状               | 治理目标                  |
| --------- | ---------------- | --------------------- |
| 组件库与业务库耦合 | 组件库代码混在业务仓       | **双仓隔离**：组件库独立仓，业务仓引用 |
| 样式不统一     | 硬编码泛滥            | **唯一 Token 源** + 自动生成 |
| 双端不同步     | iOS/Android 各自为政 | **版本铁律 + 统一发版**       |
| 无版本管理     | 无发布节奏            | **SemVer + 统一发版流程**   |

## 二、仓库架构（定稿）

```
OPC 主仓（ProductRDDept/）
├── TechMiddleOffice/            # 中台（文档权威区）
│   ├── Native-UI-Comps/         # ★ 组件库权威根（本文档所在仓库）
│   │   ├── docs/                #   数据源 + 规范 + 进度（见 docs/README.md 导航）
│   │   ├── ios/  android/       #   双端组件实现
│   │   ├── www/                 #   文档站
│   │   └── scripts/  demo/  tests/
│   ├── docs/                    # 中台通用文档
│   └── 其他业务组件仓…
└── DevOpsDept/                  # 运维（部署/审计引用）
```

技术载体：**Git Submodule**。业务仓（如 KeepAccounts）通过 submodule 挂载 `Native-UI-Comps`，随主仓锁定版本。

## 三、收纳约定（代码放哪）

### 3.1 三大物理位置

| 位置                       | 放什么                              | 权限   |
| ------------------------ | -------------------------------- | ---- |
| OPC 主仓（业务仓）              | 业务代码、业务二次开发组件                    | 业务团队 |
| 独立组件库仓 `Native-UI-Comps` | 基础组件 + foundation + 特色组件（业务分类标注） | 中台团队 |
| 子模块挂载（业务仓内）              | 引用组件库的快照（锁定版本）                   | 业务团队 |

### 3.2 迁移记录（阶段二）

- 组件库（`TMOComponent` 等）从业务仓迁出，独立为 `Native-UI-Comps`（文档即代码库）。

- 迁移完成后，业务仓只保留业务代码，不保留组件库副本。

- 迁移期间（过渡期）保留旧仓但不新增/修改；最终清理。

### 3.3 代码分类（组件库仓内）

| 分类                  | 归属           | 说明                                                    |
| ------------------- | ------------ | ----------------------------------------------------- |
| UI 组件（ui.\*）        | 组件库          | 5 子类：basics / navigation / input / display / feedback |
| 底层能力（foundation.\*） | 组件库          | 不直接展示、被组件依赖的能力                                        |
| 业务组件（业务分类）          | 组件库特色包 / 业务仓 | 按业务分类打包（见 `开发规则.md` 第四节）                              |

## 四、Submodule 挂载机制

- 业务仓挂载命令：`git submodule add <url> TechMiddleOffice/Native-UI-Comps`

- 更新：`git submodule update --remote`（显式提交子模块指针，避免漂移）

- 锁定：主仓记录 submodule commit，CI/开发者 checkout 后跑 `git submodule update --init --recursive`。

## 六、版本管理铁律（原 versioning.md）

### 6.1 版本源

- 全局唯一版本号：`docs/ui-version.json`（iOS Package.swift / Android gradle / CI 都从这里读）。

- 禁止在 iOS / Android 工程文件里手工改版本号。

### 6.2 SemVer

版本号遵循 **SemVer**：`MAJOR.MINOR.PATCH`

| 段     | 何时递增       | 示例            |
| ----- | ---------- | ------------- |
| MAJOR | 不兼容 API 变更 | 1.0.0 → 2.0.0 |
| MINOR | 向后兼容新增     | 1.0.0 → 1.1.0 |
| PATCH | 向后兼容修复     | 1.0.0 → 1.0.1 |

### 6.3 双端同步铁律

- iOS 与 Android **永远同一版本号**（以 `ui-version.json` 为准）。

- 任何一端发版，另一端必须同时发版；不允许两端版本错位。

### 6.4 版本应用位置

- `ui-version.json` 更新后，由 CI/脚本同步到：

  - iOS：`ios/Package.swift`（version: "1.0.0"）

  - Android：`android/gradle.properties`（VERSION\_NAME=1.0.0）

- 未同步即发版 → 发版不通过。

### 6.5 改组件代码即升版本（⚠️ 强制条款）

> **任何修改组件代码的行为，必须同步更新** **`ui-version.json`** **版本号 + CHANGELOG.md 对应条目。一次改动对应一次版本递增，不得跨多个改动合并升版本。**

| 改动类型                                    | 语义化版本递增         | 示例                                   | 备注                                   |
| --------------------------------------- | --------------- | ------------------------------------ | ------------------------------------ |
| 新组件新增 / 向后兼容功能扩展                        | PATCH → 或 MINOR | 1.1.6 → 1.1.7（Icon 新组件 v1.0）         | 业务逻辑无破坏                              |
| Bugfix / 视觉对齐 / Demo 调整 / .pbxproj 编译修正 | PATCH           | 1.1.7 → 1.1.8（Icon SF Symbol 名 + 间距） | 只要改了 ios/ android/ demo/ 下的组件代码，就必须升 |
| 不兼容 API 变更（组件签名/参数数量/语义改变）              | MAJOR           | 1.1.8 → 2.0.0                        | 极少触发，原则上通过「新增参数默认值」保持兼容              |

**执行步骤（改组件代码的 Agent 必走 4 步）**：

```
1. 改 ios/ 或 android/ 或 demo/ 下的组件代码      ← 解决问题
2. 升 ui-version.json 的版本号（SemVer 判定走上表）  ← 【不能漏】PATCH 即可
3. CHANGELOG.md 顶部新增对应版本条目（Fixed/Added…）  ← 写清楚改了什么/为什么改
4. git commit 三段式（改了什么/为什么改/怎么验证）    ← 规范 7d
```

违反后果：

- ❌ 版本号未升 / CHANGELOG 未写 → 提交打回重改（用户有权要求重走流程）

- ❌ 多次 Bugfix 合并升一次版本 → 追溯失效，必须每次改动单独升

- ❌ 在工程代码里硬编码修改版本号 → 以 `ui-version.json` 为唯一事实源回滚

## 七、统一发版流程

```
1. 功能完成（契约/测试/Demo 全绿，过验收门禁）
2. 更新 ui-version.json（SemVer 递增）
3. 更新 CHANGELOG.md（写变更内容）
4. 双端生成产物刷新（token、文档站）
5. CI 校验：版本号两端一致 + token 校验 + 单测全绿
6. 打 tag：v1.0.0
7. 业务仓更新 submodule 指针 + 回归
```

***

## 八、业务工程接入规范

| 步骤 | 动作                                                    |
| -- | ----------------------------------------------------- |
| 1  | 业务仓 submodule 挂载 `Native-UI-Comps`                    |
| 2  | 按需引入基础组件库包 / 业务特色组件包                                  |
| 3  | 页面用组件组合构建（禁止造轮子，见 `开发规则.md` 第五节）                      |
| 4  | 业务二次开发：继承/包装 TMO 组件，注释注明「基于 TMO `<componentId>` 二次开发」 |
| 5  | 发版后同步 submodule 指针 + 回归（含 `开发规则.md` 回归清单）             |

***

## 九、迭代流程

1. **阶段一（完成）**：组件库骨架（catalog/embedding/分类/规则）落库。
2. **阶段二（当前）**：组件完善 + 落地业务（按 `组件进度.md` 顺序 + `验收流程/` 门禁逐个推进）。
3. **阶段三（后期）**：向量化查询等扩展。

迭代节奏：每轮迭代结束更新 `组件进度.md` 达成情况，重新复算完整度指标。

***

## 十、禁止行为（团队红线）

- ❌ 组件库代码直接改在业务仓里（应提到组件库仓）。

- ❌ 不登记就私自改版本号 / 两端版本错位发版。

- ❌ 不更新唯一数据源（token/api.json/分类/版本）就发版。

- ❌ 业务仓长期挂旧版 submodule 不回归。

- ❌ 迁移完成前在旧仓新增组件。
