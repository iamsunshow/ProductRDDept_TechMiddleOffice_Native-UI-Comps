InfiniteLoading 滚动加载 · 设计规格（操作反馈区 #49 · 门禁 A）

组件 ID：ui.infinite-loading ｜ 定位：列表滚动接近底部时自动触发加载更多的底部加载状态组件——四态（idle/loading/finished/error），不代管列表内容，仅做"到底加载+状态显示"一件事，对标 TDesign Mobile List + Vant List。
组件库版本 设计阶段锁定基线 = v1.4.3（2026-09-08，未过 C2/D 不升版）

01 · 组件用途 & 不适用边界（SCQA）

维度说明
适用场景① 长列表分页加载（账目明细/消息流/商品列表），滚动接近底部自动触发 onLoadMore 回调；② 四态显示：加载中（spinner+文案）、加载完成（"没有更多了"）、加载失败（"加载失败，点击重试"）、空闲（无可展示）；③ 可配阈值：距底部多远预触发（默认 50px）
不适用（N/A）① 下拉刷新（顶部下拉触发刷新）→ PullRefresh（ui.pull-refresh）；② 列表内容容器/布局 → 宿主 LazyColumn/UITableView；③ 拖拽排序 → Drag（ui.drag）；④ 全屏遮罩加载 → Loading（ui.loading）；⑤ 骨架屏占位 → Skeleton（ui.skeleton）
五态适配默认态 ✅ idle 空闲不显示（列表正常滚动）；加载态 ✅ loading 显示 spinner+文案；完成态 ✅ finished 显示完成文案；失败态 ✅ error 显示失败文案+点击重试；禁用 N/A（由 hasMore=false 间接禁用加载）
与现有组件关系deps=[DesignTokens]（文案/颜色/间距/字号 token，零硬编码）。与 PullRefresh #55 划界：PullRefresh=顶部下拉刷新，InfiniteLoading=底部自动加载；与 Loading #50 划界：Loading=全屏/局部遮罩加载，InfiniteLoading=列表内联底部状态条；与 Skeleton #57 划界：Skeleton=首屏占位骨架，InfiniteLoading=增量加载状态

02 · 尺寸/Token 规格（零硬编码）

要素Token说明
触发阈值 threshold数字 pt/dp（默认 50）距底部多远触发加载（px 比较，iOS 距底部=contentSize.height - offset.y - bounds.height）
加载态视觉高 44pt/44dp + 居中 spinner 16×16 + loadingTextspinner 用双端各自系统动画（iOS UIActivityIndicatorView / Compose CircularProgressIndicator），颜色=textSecondary，文案=textSecondary+sizeSm
完成态视觉高 44pt/44dp + 居中 finishedText文案=textSecondary+sizeSm，无 spinner
失败态视觉高 44pt/44dp + 居中 errorText（点击重试）文案=error 色+sizeSm，点击整个 footer 触发重试 onLoadMore
文案默认值loadingText="加载中..." / finishedText="没有更多了" / errorText="加载失败，点击重试"全部可配覆盖，全部走 AppFont/AppColor token

03 · 关键决策 PREP / ACE（人为决策 4 条，编号 P1–P4，AI 代评待用户总审）

P1 · 一期形态：ACE 三选

选项后果评估
A：底部状态条模式——组件 = 底部 footer 视图 + 滚动源监听 + 四态切换 + onLoadMore 回调，列表内容由宿主提供✅ 覆盖"长列表分页加载"全部诉求；滚动源解耦=任意 LazyColumn/UITableView 可用；四态显示统一在 footer，不侵入列表 item。推荐 A：语义单一只做"到底加载+状态显示"，列表内容交给宿主（与组件库其他行为组件一致：BackTop 不代管内容）
B：自包含列表容器模式（列表+footer 封装一体，用户喂 items+itemContent）组件可 demo 即插即用，但把列表内容构建方式锁死，与页面既有 LazyColumn/UITableView 冲突。淘汰：过度封装，限制业务
C：纯监听器模式（只监听滚动触发回调，不显示状态条）状态显示交宿主自行实现，双端一致性无法保证。淘汰：四态显示是核心价值，不可省

P2 · iOS 实现路径：ACE 三选

选项后果评估
A：KVO 监听 target.contentOffset + scrollViewDidEndDecelerating 触发判定✅ 不占用业务 delegate；KVO 松耦合；距底部=contentSize.height - offset.y - bounds.height。推荐 A：与 BackTop #13 一致的 KVO 方案，行为确定代码最少
B：UIScrollViewDelegate scrollViewDidScroll 回调若业务已设 delegate 则需转发链，宿主约束多。淘汰：KVO 更松耦合
C：Timer 定时轮询 contentOffset性能差，与系统滚动事件不对齐。淘汰

P3 · Android 实现路径：ACE 三选

选项后果评估
A：参数 LazyListState + snapshotFlow 监听 visibleItemsInfo/firstVisibleItemIndex 触发判定✅ 与任意 LazyColumn 组合；snapshotFlow 派生驱动重组；距底部=layoutInfo.totalItemsCount - lastVisibleItemIndex。推荐 A：Compose 惯用、与 BackTop #13 的 scrollState 方案同源
B：组件内部自建 LazyColumn 容器（list 内容直接喂组件）与 iOS footer 模式不对齐（iOS 不代管内容）。淘汰：破坏双端同构
C：Modifier.nestedScroll 监听滚动量无法获取总高度，距底部计算不准。淘汰

P4 · 一期范围裁剪：ACE 三选

选项后果评估
A：四态全量（idle/loading/finished/error）+ 阈值可配 + 文案可配 + onLoadMore 回调 + error 点击重试✅ demo 四段可 1:1 验收；四态覆盖全部加载场景，error 重试是高频刚需。推荐 A：范围收敛但覆盖完整
B：一期仅 loading 态（无 finished/error）无法表达"没有更多"和"加载失败"，体验残缺。淘汰：finished/error 是基础体验
C：一期即支持自定义 spinner/footer slot自定义 slot 增加复杂度，且与"四态统一显示"矛盾。淘汰：登记二期

05 · 平台差异表（表内放行，表外必须双端统一）

维度iOSAndroid放行原因
滚动源UIScrollView 引用（KVO contentOffset）LazyListState 参数（snapshotFlow 派生）系统级原生差异：两端滚动模型不同（对象引用 vs 状态快照）
距底部计算contentSize.height - offset.y - bounds.heighttotalItemsCount - lastVisibleItemIndex语义一致：均为"剩余可见距离"（表内放行）
spinner 动画UIActivityIndicatorView（系统菊花）CircularProgressIndicator（Compose 圆形进度）系统级原生差异：各自系统加载动画
触发判定时机scrollViewDidEndDecelerating + KVO 阈值交叉snapshotFlow 最后可见 item 变化语义一致：均为"滚动接近底部时触发"（表内放行）
四态文案UILabel 文本Text 文本同一文案双端渲染（表内放行）
