# TMO 组件库 · 开发规则（组件规则 + API 契约 + Schema）

> 地位：**组件开发与双端对齐的唯一规则文档**。命名、分类收口、特色组件打包、业务库约束、
> API 完善路径、api.json 字段规范、双端 API 契约，均以本文件为准。
> 2026-08-30 由原 `component-rules.md` + `api-contract.md` + `component-schema.md` 三合一。
>
> 名词约定：**TMO** = TechMiddleOffice（中台技术部）。无特殊说明时，「TMO」「TMO组件库」即指 `Native-UI-Comps`（组件库权威根）。
>
> 配套：**验收标准**（设计先行 / API check / 测试门禁 / CR / 自研率）见 `docs/验收流程/验收标准.md`；
> **设计规范**（Token 铁律）见 `docs/设计规范.md`；**治理/版本/收纳**见 `docs/治理规范.md`。

## 一、目标与优先级（拉齐）

| 阶段 | 目标 | 说明 |
|------|------|------|
| 现在（重中之重） | **完善组件库 + 落地业务库** | 组件补齐、双端 API 对齐、特色组件按业务分类打包；业务库全部页面基于 TMO 组合/二次开发 |
| 后期 | **向量化查询及扩展功能** | 在已有 `embed.py/search.py/api.json/embeddings` 基础上增量完善，非从零 |

**完善的验收标准：**
- 组件分类完整度指标（见 `组件分类.md`，当前基线 25.3%）持续提升
- 双端组件 Props/事件/回调 100% 对齐（见第八节「双端 API 契约」）
- 业务 App 页面组件 100% 来自 TMO 组件库组合或二次开发，零自造轮子

## 一点五、改组件代码即升版本（⚠️ 强制前置 · 改代码前必看）

> 详见 `docs/治理规范.md` §6.5。**本条款优先级高于本文其他所有规则。**

| 改动类型 | 版本递增 | 示例 |
|----------|---------|------|
| 新组件新增 / 功能扩展 | PATCH 或 MINOR | 1.1.6 → 1.1.7（Icon 新增） |
| Bugfix / 视觉对齐 / Demo 调整 / .pbxproj 修复 | PATCH | 1.1.7 → 1.1.8（Icon Symbol + 间距） |
| 不兼容 API 变更 | MAJOR | 极少触发 |

**必走 4 步（少一步都不算完成）**：
1. 改 `ios/` 或 `android/` 或 `demo/` 组件代码
2. 升 `docs/ui-version.json` 版本号
3. `CHANGELOG.md` 顶栏新增对应版本条目
4. git commit 三段式（改了什么/为什么改/怎么验证）

## 二、组件分类收口（唯一文档）

- 组件分类**唯一收口**到 `Native-UI-Comps/docs/组件分类.md`，不再散落其他目录。
- 分类基准：**NutUI React 4.x 官网左侧菜单树**（8 类：基础/布局/导航/数据录入/操作反馈/展示/特色 + 底层能力），与业务组件库无关的组件不入此表。
- `TechMiddleOffice/docs/design-spec/` 只放**设计相关细节**（Token 对比、视觉规格等），不放组件分类。
- 各文档提及分类时，以 `组件分类.md` 为唯一依据。

## 三、沟通语言机制

- 组件名称表 = **页面描述语言**。描述界面时用「组件名 + 属性（variants）」表达，如「Empty 空状态 + 图标 + 主文案」。
- 特殊/新需求：先按特色组件准入标准评审（见第四节），通过后进组件库，**扩充名词表**。
- `api.json` 的 `subcategory` 字段必须与 `组件分类.md` 分类一致，保证「词汇」有稳定 id 锚点（如 `ui.avatar`）。

---

## 四、特色组件与打包机制

1. **特色组件按业务分类**：属于哪个业务，分类就标哪个业务（如 `业务：记账`）。
2. **打包分离**：
   - **基础组件库包**：NutUI React 4.x 参考分类组件 + 底层能力（foundation）→ 随 TMO 组件库统一打包分发。
   - **业务特色组件包**：业务特色组件**不进入基础组件库包**，按业务单独打包，业务侧按需引入。
3. **特色组件准入标准**：跨业务可复用 → 进基础库；单一业务强绑定 → 进业务特色包并标注业务。
4. 当前归属（详见 `组件分类.md`）：
   - 特色组件·通用：Calendar 日历工具 / SystemBars 系统栏 / DesignTokens 设计令牌（跨业务，随基础库）。
   - 特色组件·业务：GridPicker 宫格选择 / Split 双栏行 / Statistic 汇总统计（标注所属业务，进业务特色包）。

## 五、业务库约束（禁止造轮子）

业务代码库中的组件**必须**基于 TMO 组件库构建或二次开发：

1. **新增业务组件前检查清单**：
   - TMO 有 → 直接组合使用。
   - TMO 有近似 → 继承/包装扩展（保留原组件 id，扩展 variants），并在代码注释注明「基于 TMO `<componentId>` 二次开发」。
   - TMO 完全没有 → 先走特色组件评审（第四节），**通过后再开发**，不得先开发后补登记。
2. 业务库不允许出现与 TMO 重复的轮子；发现即提升为 `ui.*` 或业务特色组件并迁移。
3. 判定口诀：**能被两个以上不同业务复用的 → 进组件库；只服务一个业务的 → 留业务做二次开发。**

## 六、API 完善路径（降低开发成本）

```
分类名词表（组件分类.md）
        ↓ 每个组件定义唯一 id + subcategory
api.json（metadata 单一数据源，含 props/events/demos/note）
        ↓ 双端 100% 对齐
第八节「双端 API 契约」（唯一权威清单）
        ↓ 双端并行实现
iOS（Swift SPM）+ Android（Kotlin Gradle）
```

- 每个新增/完善的组件：先定契约 → 双端对齐实现 → Demo 更新 → 统一发版（见 `docs/治理规范.md`）。
- 状态统一：默认 / 禁用 / 加载 / 成功 / 失败；交互、弹窗层级、点击反馈双端一致。

## 七、组件元数据 Schema（api.json 字段规范）

组件 metadata 单一数据源为 `docs/api.json`（单个 JSON 对象，`components` 数组内每组件一条；方案 B 前为 `catalog/components.jsonl`，每行一条）。

### 7.1 api.json 顶层

| 字段 | 类型 | 说明 |
|------|------|------|
| `version` | string | metadata 版本 |
| `updatedAt` | string | 最近更新时间（ISO 8601） |
| `componentCount` | int | 组件库组件数量（`components` 数组长度） |
| `components` | object[] | 组件库成员（仅 `ui` + `foundation`；字段见下表） |
| `businessExtensions` | object[] | 业务层二次开发产物（非组件库成员，由各 App 继承基础组件开发） |
| `businessExtensionCount` | int | 业务扩展数量 |

### 7.2 每组件字段（`components[]` 元素）

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `id` | string | 是 | 稳定 ID，如 `ui.empty` |
| `name` | string | 是 | 显示名 |
| `category` | string | 是 | `ui`（UI 组件）\| `foundation`（底层能力） |
| `subcategory` | string | 否 | UI 五子类之一：`basics` \| `navigation` \| `input` \| `display` \| `feedback`（仅 `ui` 有） |
| `summary` | string | 是 | 一句话功能 |
| `description` | string | 否 | 详细描述（用于向量化检索，包含功能说明、设计要点） |
| `scenarios` | string[] | 否 | 典型应用场景（如「商品列表为空」「搜索无结果」） |
| `capabilities` | string[] | 是 | 检索标签 |
| `used_in_apps` | string[] | 否 | 跨 App 使用追踪（可手动标注；不填时由 `source_refs` 自动提取） |
| `visual_tokens` | string[] | 否 | 依赖 token 名 |
| `platforms` | object | 是 | 见 7.3 |
| `apis` | string | 否 | 对外接口摘要 |
| `deps` | string[] | 否 | 依赖的 component id |
| `source_refs` | object | 否 | `{ ios?, android?, harmony?, weixin?, alipay?, note? }` — 路径中 `App/<名>` 自动提取为 `used_in_apps` |
| `variants` | string[] | 否 | 视觉/功能变体 |
| `anti_goals` | string[] | 否 | 不适用场景 |
| `search_text` | string | 是 | embedding 语料 |
| `embedding_ref` | string | 否 | 向量文件相对路径 |
| `status` | string | 是 | `draft` \| `stable` \| `deprecated` |

> `visual_refs`（截图路径）字段已随 2026-08-30 视觉资产淘汰（svg/截图 → H5 规格页）废弃，不再填写。

### 7.3 platforms

```json
{
  "ios": { "state": "available", "note": "" },
  "android": { "state": "partial", "note": "能力弱于 iOS" },
  "harmony": { "state": "unavailable", "note": "" },
  "weixin": { "state": "unavailable", "note": "" },
  "alipay": { "state": "unavailable", "note": "" }
}
```

`state`: `available` | `partial` | `unavailable`

### 7.4 元数据够用性结论

- **一期够用**：上表支撑「说诉求 → 检索 → 拼装清单 → 按端改代码」
- **二期增强**：多端真实实现路径、契约测试、版本 semver
- **向量化增强**：`description` + `scenarios` 字段丰富 embedding 语料，提升自然语言检索精度

### 7.5 向量化字段说明

embedding 语料（`search_text`）由以下字段拼接生成：

```
{id} {name} {summary} {description} {category} {capabilities...} {scenarios...} {industry_names...} {legacy_id}
```

| 字段 | 向量化贡献 | 说明 |
|------|-----------|------|
| `name` | 高 | 组件名是核心检索词 |
| `summary` | 高 | 一句话描述功能 |
| `description` | 中 | 详细功能说明，补充语义 |
| `scenarios` | 高 | 用户常以场景描述需求（如「空态」「选择日期」） |
| `capabilities` | 中 | 技术标签/别名 |
| `industry_names` | 中 | 业界通用名，跨库检索桥梁 |

## 八、双端 API 契约（唯一权威清单）

> 双端组件 Props/参数/状态/回调 **100% 对齐**。本文以 iOS 现有实现为基准，
> 逐步补齐 Android 对应实现，作为双端 API 契约的唯一权威清单。
>
> 约定：列出每个组件的**对外 API（构造参数、绑定方法、回调）**与**状态规范**。
> Android 侧必须提供同名/同语义的参数与回调；命名允许平台惯例外（Swift camelCase / Kotlin camelCase），
> 但**语义与数量必须一致**。

> 状态统一：**默认 / 禁用 / 加载 / 成功 / 失败**（组件支持哪些在各自章节标注）。

### 8.4 契约执行铁律

- 新增/修改组件 API，**先改本文，再改双端代码**。
- 两端参数数量与语义必须一致；仅命名可随平台惯例。

- 业务强相关组件不进库、不入契约（见 8.1 末尾说明）。
