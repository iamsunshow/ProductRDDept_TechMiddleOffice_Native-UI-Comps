PullToRefresh 下拉刷新 · 设计规格（操作反馈区 #55 · 门禁 A）

组件 ID：ui.refresh ｜ 定位：列表/可滚动内容下拉触发刷新的容器组件——用户在内容顶部下拉，露出刷新指示器（灰圈+文案），松手达到阈值触发 onRefresh 回调，业务完成后将 refreshing 设为 false 收起指示器。对标 iOS UIRefreshControl + Android SwipeRefreshLayout（本库采用 iOS 风格=非浮层顶开内容）。
组件库版本 设计阶段锁定基线 = v1.4.13（2026-09-09，未过 C2/D 不升版）

01 · 组件用途 & 不适用边界（SCQA）

维度说明
适用场景① 列表内容下拉刷新（账目列表/消息流/商品列表），下拉顶开内容露出刷新指示器，松手触发 onRefresh；② 受控 refreshing=true 时指示器保持显示，业务刷新完成后 refreshing=false 收起；③ 可配刷新文案 title；④ 可禁用 enabled=false
不适用（N/A）① 底部加载更多 → InfiniteLoading（ui.infinite-loading）；② 全屏遮罩加载 → Loading（ui.loading）；③ 首屏骨架占位 → Skeleton（ui.skeleton）；④ 拖拽排序 → Drag（ui.drag）；⑤ 侧滑操作 → Swipe（ui.swipe）
五态适配下拉态 ✅ 用户下拉时指示器随下拉距离露出（灰圈进度环+文案）；刷新态 ✅ 松手达到阈值→onRefresh→refreshing=true→指示器停在刷新位置（旋转中+文案）；完成态 ✅ refreshing=false→指示器收起动画；禁用 N/A（enabled=false 时不响应下拉）
与现有组件关系deps=[DesignTokens]（颜色/间距/字号 token，零硬编码）。与 InfiniteLoading #49 划界：PullToRefresh=顶部下拉手动触发刷新，InfiniteLoading=底部滚动自动加载更多；与 Loading #50 划界：Loading=全屏/局部遮罩加载，PullToRefresh=列表内联顶部下拉指示器

02 · 尺寸/Token 规格（零硬编码）

要素Token说明
触发阈值 threshold72dp/pt下拉距离达到阈值时松手才触发刷新；未达阈值则回弹收起
最大下拉距离 maxPullthreshold × 1.6下拉阻尼：超过阈值后继续下拉有阻尼感，最大不超过 maxPull
刷新停留高度 hold64dp/ptrefreshing=true 时指示器停留的高度
指示器圆圈22×22 dp/pt，strokeWidth=2，color=textSecondary下拉中=进度环（progress=pull/threshold）；刷新中=旋转环
刷新文案textSecondary + sizeSm（14）默认 "下拉刷新数据"，可配 title 覆盖；下拉距离>15%阈值时显示
指示器区域背景bgCard（白色）下拉露出的区域背景与内容背景一致，非浮层
收起动画tween 200-220msrefreshing=false 时指示器平滑收起

03 · 关键决策 PREP / ACE（人为决策 4 条，编号 P1–P4，AI 代评待用户总审）

P1 · 组件形态：ACE 三选

选项后果评估
A：内容包裹器模式——PullToRefresh(refreshing, onRefresh) { content }，组件管理下拉手势+指示器，内容由宿主提供✅ 双端同构（iOS/Android 都是 wrapper）；与 InfiniteLoading #49 footer 模式同源=不代管内容；宿主可用任意滚动容器（LazyColumn/UITableView/ScrollView）。推荐 A：职责单一=只做"下拉手势+指示器+onRefresh"，内容交宿主
B：自包含列表容器模式（PullToRefresh(items, itemContent) 内部建列表）demo 即插即用，但锁死列表构建方式，与宿主既有列表冲突。淘汰：过度封装
C：纯手势监听+回调模式（只监听下拉触发 onRefresh，不显示指示器）指示器交宿主自行实现，双端一致性无法保证。淘汰：指示器是核心价值

P2 · 指示器风格：ACE 三选

选项后果评估
A：iOS 风格——下拉顶开内容露出指示器区域（非浮层），灰圈进度环+文案，刷新时旋转✅ 双端视觉完全一致（Android 已实现 IosStylePullRefresh 顶开模式）；非浮层=不遮挡内容；与 NutUI/Vant PullRefresh 顶开模式一致。推荐 A：双端同构，已有 Android 实现可复用
B：Android Material 风格——SwipeRefreshLayout 浮层圆圈盖在列表上方Android 原生体验好，但与 iOS 视觉差异大（浮层 vs 顶开）。淘汰：破坏双端一致性
C：纯下拉箭头+下拉刷新文案（无圆圈）视觉简单，但缺少刷新中旋转动效，体验差。淘汰

P3 · iOS 实现路径：ACE 三选

选项后果评估
A：UIRefreshControl（系统原生）+ 适配 content inset✅ 系统原生下拉刷新，灰圈+文案，动画自然；但 UIRefreshControl 是浮层在列表上方（非顶开），与 Android 顶开模式视觉略有差异。推荐 A：系统原生稳定可靠，视觉差异在可接受范围（均为灰圈+文案），UIRefreshControl 的浮层是 iOS 用户习惯
B：自定义 UIScrollView 包装+KVO contentOffset 顶开内容与 Android 顶开模式完全一致，但需自行实现下拉阻尼/阈值/动画，代码量大。备选：若用户要求双端顶开一致则选 B
C：UITableView 子类封装（现有 PullRefreshTableView）只能用于 UITableView，不能包装任意滚动内容。淘汰：限制宿主容器类型

P4 · Android 实现路径：ACE 三选

选项后果评估
A：NestedScrollConnection + graphicsLayer translationY 顶开内容（现有 IosStylePullRefresh 方案）✅ 已实现且验证通过；顶开模式与 iOS UIRefreshControl 视觉一致；阻尼/阈值/动画完整。推荐 A：复用现有实现，只需适配 API 契约（refreshing 受控+title+enabled）
B：SwipeRefreshLayout（Android 原生）浮层圆圈，与 iOS 顶开模式不一致。淘汰：破坏双端一致性
C：Modifier.pullRefresh（Compose 实验性 API）实验性 API 不稳定，且是浮层模式。淘汰

07 · anti_goals 反目标（二期不做）

  • 自定义下拉头部样式（如品牌动画/下拉图片）—— 一期统一灰圈+文案
  • 下拉刷新同时触发加载更多（与 InfiniteLoading 组合由宿主自行编排）
  • 多类型刷新指示器（Material 浮层/经典下拉箭头）—— 一期只做 iOS 风格
  • 下拉刷新成功/失败提示（交 Notify/Toast 组件）
