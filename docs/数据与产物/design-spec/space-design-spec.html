Space 间距 · 设计规格（布局组件 #4 · 任务清单 #11，subcategory=layout · 门禁 A）

组件 ID：ui.space ｜ 定位：纯间距容器（一组任意子内容按统一档位间距排布，水平/垂直），对标 Ant Design Space 的轻量版。用于「icon+文字工具组、chip 操作组、卡片间隔、表单块纵向间距、多行条目间距」等只需统一间距、无比例诉求的场景。
组件库版本 设计阶段锁定基线 = v1.4.0（2026-09-04，未过 C2/D 不升版）

01 · 组件用途 & 不适用边界（SCQA）

维度说明
适用场景① 工具/操作组（「记一笔」「扫一扫」「分享」等 icon+文字横向组，间距默认紧凑 8）；② chip 筛选/标签组（横向一排，sm 8）；③ 两张卡片/区块之间的显式间距（如 lg=16/xl=24）；④ 表单或详情纵向堆叠的多行文本/条目（vertical 方向，md/lg 档）；⑤ 图标+文字水平单元组（同一单元内部再规整间距）
不适用（N/A）① 需要按比例分栏（1:1 / 4+8）→ Layout（ui.layout）；② 等分宫格入口矩阵 → Grid（ui.grid）；③ 整行列表项/可点容器 → Cell（ui.cell）；④ 任意两点间距（margin/padding 单次需求）→ 直接用 AppSpace token 排版即可（不必包 Space）；⑤ 分隔线 → Divider（ui.divider）（Space 不做 split 分隔符，一期裁剪见 P4）
五态适配Space 为「纯间距容器」，无自身交互与状态。默认态 ✅ = 子项按 direction/size 均匀排布、首尾无 padding。点击/禁用/加载/成功/失败 N/A（子项自身状态由内容组件承担）
与现有组件关系deps=[DesignTokens]（AppSpace）零硬编码。与 Layout 划界：Layout=比例分栏（span 体系，面向「按比例分配宽」），Space=统一间距（面向「等比/自然宽子项只需间距」）。LayoutRow 内部子项间隔用 gutter，Space 只管理子项排布不承载比例；两者可嵌套（Layout Col 内放 Space 组 / Space 子项放 Layout 行）。与 Divider 互补：需要「内容 + 分隔线」交替用 split 的场景一期交 Divider 文本模式或子项自含，Space 不内建分隔符

02 · 尺寸/颜色/圆角 Token 规格（零硬编码，引用 design-token.json）

要素Token数值说明
子项间距（size）AppSpace.xs~xl4/8/12/16/24相邻子项统一间距（首尾无 padding）；默认档位待 P3 表决
排布方向规则horizontal / vertical水平=一行从左到右；垂直=一列从上到下。direction 由调用方传入，默认 horizontal（P1 表决后定）
子项对齐规则水平=顶部对齐；垂直=起始侧（左）对齐一期固定（对齐由内容自身高度/宽度自然决定，Space 不拉伸子项）；center 对齐 / 两端铺满二期候选
容器背景/边框/圆角/文本—透明 / 无Space 为 pass-through 容器：零绘制零自有文本，装饰由子项内容承担

03 · 关键决策 PREP / ACE（人为决策 4 条，编号 P1–P4，待用户门禁 A 表决）

P1 · 方向支持：ACE 三选

选项后果评估
A：单组件 + direction 双向（horizontal / vertical）✅ 一个 API 覆盖「横向工具组」与「纵向条目堆叠」两类高频场景；与 Ant Design Space 对齐；双端实现 = iOS UIStackView.axis / Android Row|Column，成本低。推荐 A：覆盖最广、API 最简、双端同构
B：仅 horizontal（一期）砍掉纵向需求（表单/详情多行间距等），但业务侧会退回手动加 padding/margin 逐行处理，间距失去统一档位约束。淘汰：纵向堆叠间距是高频诉求，只做横向价值减半
C：双容器 SpaceH / SpaceV（按方向分两个类）免 direction 参数但多一个类型；Android 声明式里 lambda scope（RowScope/ColumnScope）更明确，但双端命名/心智成本高于单组件。淘汰：单组件 + direction 足够，双类过度设计

P2 · size 档位模型：ACE 三选

选项后果评估
A：AppSpace 五档枚举（xs/sm/md/lg/xl）✅ 间距档位与全库 token 对齐（4/8/12/16/24），跨组件节奏一致、可读性强；超纲需求（如 20）业务应回到 token 决策而非在 Space 造数。推荐 A：档位约束防止「每个页面一个间距」的漂移
B：三档裁剪（sm/md/lg）选项更少但 xs（贴紧 4）与 xl（区块级 24）两类真实场景无档可用，会退回硬编码。淘汰：裁剪反致越权硬编码
C：纯数字 Dp/pt（任意数值）最灵活但失去档位约束：页面间 9/10/11 漂移，且与 Layout gutter 档位语义不统一。淘汰：无约束即无设计系统

P3 · size 默认值：ACE 三选

选项后果评估
A：默认 AppSpace.sm=8✅ 与 Ant Design Space 默认 small=8 对齐；Space 语义=紧凑内容组（icon+文字工具行 / chip 组 / 双按钮行），默认即常用；需宽间隔（卡片间距/纵向表单块）时业务显式传 md/lg/xl。推荐 A：紧凑默认贴合 Space 最常见用法，Ant 生态对齐降低认知
B：默认 AppSpace.md=12与 Layout gutter 默认一致（页面级节奏 12），但 Space 工具组默认 12 偏松（两组按钮间距 12 视觉散），多数调用仍需传 sm。淘汰：默认 md 会令高频紧凑场景多写参数
C：默认 lg=16偏宽松，工具组/文本行默认 16 过散。淘汰：默认过松与 Space 紧凑语义冲突

P4 · 一期范围裁剪（wrap 换行 / split 分隔符）：ACE 三选

选项后果评估
A：一期仅 direction + size（wrap / split 均登记二期候选）✅ 覆盖工具组/条目堆叠/区块间隔全部一期场景；实现 = iOS UIStackView / Android Row|Column（原生能力），双端零差异；chips 自动折行与「内容/分隔线交替」两类场景出现真实诉求后再立项。推荐 A：一期克制，双端一致，二期候选已登记
B：一期追加 wrap（子项超宽自动折行）Android FlowRow 现成，但 iOS 需自实现流式布局（UIStackView 不支持 wrap）→ 双端实现不对称、风险与工期高。淘汰：iOS 成本高且属 chips 流式独立场景（届时立项论证）
C：一期追加 split（子项间插入分隔符，如 "/"、竖线）「面包屑」「多段日期」「a/b/c」类好看，但需分隔视图类型设计与内容/间距联动；现有 Divider 文本模式可近似，且此类场景当前业务未出现。淘汰：无真实诉求不预埋复杂 API；登记二期候选

05 · 平台差异预告

维度iOSAndroid差异说明
容器实现UIStackView（axis = direction 映射；spacing = size 档位 pt）Compose Row / Column（direction 分支）+ Arrangement.spacedBy(size)系统原生架构差异；间距数学语义一致（档位 token 数值），行为对齐
子项对齐StackView 默认：横向 top、纵向 leading；不做 fill（拉伸由子项自行）Row verticalAlignment=Top；Column horizontalAlignment=Start双端一致（一期固定，center 拉伸二期）
size 档位AppSpace 同名字段（CGFloat pt）AppSpace 同名字段（Dp）design-token.json 单源（4/8/12/16/24）
命名Space（iOS 无系统同名冲突；规则：不加 View 后缀）Space（Compose 无同名内置，避开 Spacer）双端同名同 API

06 · API 速览（门禁 B 冻结前草案）

类别名称类型必填说明
Space Propsdirection'horizontal' \| 'vertical'否排布方向（默认 horizontal，P1 表决后定）
Space PropssizeAppSpace 档位（xs/sm/md/lg/xl）否相邻子项间距（默认 P3 表决后定=推荐 sm 8）
Children—任意 View/Composable（2 个及以上）—子项任意内容组件（文本/按钮/chip/卡片/嵌套 Space/Layout 行）；少于 2 项时空排布自然无异常
事件———Space 无事件；子项交互由内容组件自身事件承担

使用示例（草案）：Space(direction: .horizontal, size: .sm) { 记一笔 · 扫一扫 · 账单 } / Space(direction="vertical", size="md") { …详情行×N }
